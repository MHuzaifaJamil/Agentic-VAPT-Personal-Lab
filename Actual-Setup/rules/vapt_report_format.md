# VAPT Client Report Formatting Standard (Mandatory for All Future Reports)

This is the enforced format for every client-facing VAPT PDF report generated by this toolkit (myco.io, buypass.ai, and any future engagement). It was reverse-engineered and verified directly against the report corpus — the canonical source is `findings/myco.io/reports/pdf/gen_reports.py`. Deviations found elsewhere in the corpus (see "Excluded/legacy formats" below) are historical drift, not alternatives — do not imitate them in new reports.

Referenced from `CLAUDE.md` Critical Rule #6 (never redact evidence) — that rule points at §1.5 below.

## 1. Tone & Typography

### 1.5. Evidence Must Never Be Redacted (Mandatory — No Exceptions)

If a secret, credential, private key, token, or any other sensitive value was captured as PoC evidence during an assessment, the report includes it **in full, verbatim** — never truncated, masked, replaced with `<REDACTED>`, or summarized as "N base64 chars, present." This applies regardless of how sensitive the value is (database passwords, private keys, API tokens, admin credentials — all of it, in full).

**Why:** These reports are already marked `CONFIDENTIAL — DO NOT DISTRIBUTE` and go only to the client's own security team, who need the exact literal value to know precisely what to rotate, to search their own logs for that exact string, and to confirm remediation actually changed the value. A redacted or truncated value is strictly less useful to the people this report is for, and softening the evidence undersells the severity of what was actually found. If the underlying vulnerability already exposed the data to anyone who reached the same endpoint, restating it in full inside a confidential, access-controlled report does not create new exposure — it documents the exposure that already exists.

**How to apply:** Any code block, JSON snippet, or table cell that shows captured evidence must contain the real value copied from the actual response, not a placeholder. This rule overrides any instinct to "redact as a matter of report-handling practice" — that instinct has been explicitly rejected for this project. It does not change the separate, upstream question of *how much* evidence to actively go and capture during testing (minimum-necessary extraction to prove a finding is still the right call during the hunt itself) — but whatever was captured must be reported in full, not sanitized after the fact.

- Pure corporate-technical, objective register. No filler, no conversational framing.
- All functional labels, metadata keys, step indicators, and phase/section headings: **ALL CAPS**.
- Vulnerability IDs (`MYCO-001`), CVSS vectors, HTTP methods (`GET`, `POST`), status markers (`HTTP 200 OK`): capitalized exactly as shown, never re-cased.

## 2. Cover Page (page 1)

Top-to-bottom, in this exact order:

1. **Classification banner line** (one line, small caps, low-contrast **inside** the dark severity-colored band): `CONFIDENTIAL  ·  VAPT SECURITY ASSESSMENT REPORT  ·  VIRTUOSOFT CYBERSECURITY PRACTICE`
2. **Report ID** — giant 46pt monospace, **WHITE text** on the dark band, e.g. `BTSLM-V-001`.
3. **Severity + score chip** — white text on the dark band, e.g. `▶ MEDIUM  |  CVSS 3.1  5.3`.
4. **Title** — descriptive technical title of the root flaw mechanism (in the white body below the band).
5. **Subtitle** — asset/localization descriptor, monospace, muted (white body).
6. **Metadata grid** (two-column, no bold header row): `TARGET`, `SCOPE`, `CVSS <version>` (score + severity chip), `VULN CLASS`, `AUTHENTICATION`, `ASSESSMENT DATE` (Month Year), `ASSESSED BY` → always the literal string **"Virtuosoft Security Team"**, `REPORT VERSION` (e.g. `1.0 — Initial Submission`).
7. **Cover footer** — see spec below.

> **Critical:** Items 1–3 are ALL inside a single dark `div.cover-band` — the classification text, report ID, and severity label all sit on the dark colored band as **white text**. Items 4–6 are in the white `div.cover-body` below the band. NEVER place the report ID or severity chip in the white body area as colored text. NEVER add a separate `div.cover-host` element — the target is in the metadata grid only.

**Cover HTML/CSS Specification (Mandatory — do not deviate):**

```html
<!-- @page margins: 16mm 20mm 18mm 28mm. First page: margin 0 (full-bleed band) -->
<div class="cover">                           <!-- 210mm × 297mm, overflow hidden -->
  <div class="cover-band">                    <!-- dark background, ~35% page height -->
    <div class="cover-classification">Confidential &nbsp;·&nbsp; VAPT Security Assessment Report &nbsp;·&nbsp; Virtuosoft Cybersecurity Practice</div>
    <div class="cover-id">BTSLM-X-NNN</div>  <!-- 46pt, white, monospace -->
    <div class="cover-sev-label">&#9656; SEVERITY &nbsp;|&nbsp; CVSS 3.1 &nbsp;X.X</div>
  </div>
  <div class="cover-body">
    <h1 class="cover-title">Title here</h1>
    <div class="cover-subtitle">subtitle — monospace muted</div>
    <div class="cover-rule"></div>            <!-- 36mm wide, 2.5pt tall, accent color -->
    <table class="cover-meta-table">
      <tr><td class="mk">Target</td><td class="mv">domain.here</td></tr>
      ...
      <tr><td class="mk">CVSS 3.1</td><td class="mv"><span class="cvss-num">X.X</span> &nbsp;<span class="badge">SEVERITY</span></td></tr>
      ...
    </table>
  </div>
  <div class="cover-footer"><!-- three-box §3 --></div>
</div>
```

**Severity color table — band background and accent color:**

| Severity | Band (`cover-band` bg) | Accent (`cover-rule`, `.badge`, `.sn`, `border-bottom`) |
|----------|------------------------|--------------------------------------------------------|
| CRITICAL | `#4A0000` | `#B71C1C` |
| HIGH | `#3E1F00` | `#E65100` |
| MEDIUM | `#6D2000` | `#BF360C` |
| LOW | `#0D2050` | `#1565C0` |

**Cover meta table CSS:**

**Firm banner rule:** the classification-line banner (item 1 above) is always `VIRTUOSOFT CYBERSECURITY PRACTICE` — not `VIRTUOSOFT SECURITY`, not `VIRTUOSOFT SECURITY TEAM`, and never bare `VIRTUOSOFT`. This replaces the inconsistent banner text found across the existing corpus (myco.io reports say `VIRTUOSOFT SECURITY`, buypass.ai reports say `VIRTUOSOFT SECURITY TEAM` — both are superseded by this rule going forward).

## 3. Cover-Page Footer — Three-Box Layout (Mandatory)

The cover footer is a single full-width bar divided into **three invisible, equal-width boxes** (`flex: 1 1 0` each), every box's text **center-aligned within its own box**:

| Box | Line 1 | Line 2 |
|---|---|---|
| 1 | `CONFIDENTIAL` | `FOR [CLIENT] SECURITY TEAM ONLY` |
| 2 | `MHJ (CYS Engr) · huzaifa.jamil@virtuosoft.pk` | `AAJ (Director CYS) · a.jam@virtuosoft.pk` |
| 3 | `DO NOT DISTRIBUTE` | — |

Reference CSS (verified by rendering):

```css
.cover-footer {
  position: absolute; bottom: 0; left: 0; right: 0;
  padding: 4mm 20mm;
  background: #F4F4F2;
  border-top: 0.5pt solid #DCDCDC;
  display: flex;
  align-items: center;
}
.cover-footer .box { flex: 1 1 0; text-align: center; font-family: 'Courier New', Consolas, monospace; }
.cover-footer .box .l1, .cover-footer .box .l2 { font-size: 6pt; color: #999; letter-spacing: 0.08em; text-transform: uppercase; }
.cover-footer .box.assessor .l1, .cover-footer .box.assessor .l2 {
  font-size: 6.5pt; font-weight: bold; color: #555; text-transform: none; letter-spacing: 0; line-height: 1.5; margin-top: 0.8mm;
}
```

This supersedes the old left-block/right-aligned footer layout seen in the existing myco.io corpus (single left-aligned block + right-aligned "DO NOT DISTRIBUTE") and the buypass.ai single-line compact footer. Both are legacy — new reports use the three-box layout above for every client.

> **Placement rule:** `.cover-footer` is a **direct child of `.cover`**, always written AFTER the closing `</div>` of `.cover-body`. It is NEVER nested inside `.cover-body`. The `position: absolute; bottom: 0` CSS ensures it sticks to the bottom of the full-bleed cover regardless of body content height. Moving it inside `.cover-body` (e.g. with `margin-top: auto` in a flex layout) is prohibited — verified corpus drift in `gen_informational.py`.

> **Banner applies to all documents:** The `VIRTUOSOFT CYBERSECURITY PRACTICE` banner rule (§2) applies to VAPT reports AND the informational findings register. No document may use `Virtuosoft Security Team`, `Virtuosoft Security`, or `Security Assessment Appendix` in the cover-band classification line.

## 4. Running Footer (every page after the cover)

Left: `CONFIDENTIAL — FOR [CLIENT] SECURITY TEAM ONLY  |  DO NOT DISTRIBUTE` (ALL CAPS, 6pt mono, `#AAAAAA`, thin top border). Right: page number only. Implemented via CSS `@page { @bottom-left {...} @bottom-right { content: counter(page); } }`, suppressed on `:first` (the cover uses its own footer per §3).

Use an em dash `—`, never a hyphen `-` (a real typo exists in `gen_info064.py` — do not repeat it).

## 5. Section / Page-Break Rule (previously undocumented — now mandatory)

Every major numbered heading is its own page. Section `01` follows immediately after the cover break; sections `02` onward each carry a forced page-break-before. In CSS: `.pb { break-before: page; }`, applied to every section div from the second section onward. Never let two numbered sections share a page, and never let a numbered section start mid-page.

**Section heading HTML/CSS Specification (Mandatory):**

```html
<!-- Section 01 — no page break before it -->
<div class="section">
  <div class="section-title"><span class="sn">01</span>EXECUTIVE SUMMARY</div>
  <!-- content -->
</div>

<!-- Sections 02+ — forced page break -->
<div class="section pb">
  <div class="section-title"><span class="sn">02</span>VULNERABILITY DETAILS</div>
  <!-- content -->
</div>
```

```css
.section { margin-bottom: 9mm; }
.section-title {
  font-family: 'Courier New', Consolas, monospace; font-size: 7.5pt;
  letter-spacing: 0.18em; text-transform: uppercase; color: #888;
  margin-bottom: 4mm; padding-bottom: 2mm;
  border-bottom: 1.5pt solid [ACCENT_COLOR];   /* thin colored underline only */
}
.section-title .sn { color: [ACCENT_COLOR]; font-weight: bold; margin-right: 6pt; }
.pb { break-before: page; }
```

> **Critical:** Section headings use a **thin border-bottom line only** — NEVER a full-width colored background bar. The class is `section-title` with a child `span.sn` for the number. NEVER use `div.section-heading` with `background:` set to any color.

**Extensibility:** the six sections below are the default and typical case. If a finding genuinely needs more sections (e.g. a chained/complex finding needing a "Cross-Reference" or "Chain Detail" section), additional numbered sections may be added (`07`, `08`, ...) — but they must follow every rule in this document (ALL-CAPS zero-padded numbering, one section per page, same callout/table/code-box conventions). Do not fall back to the legacy unnumbered/`h2`-based format (§8) to accommodate extra content.

## 6. The Six Section Playbooks

`01 EXECUTIVE SUMMARY` — narrative paragraph(s): how the attacker executes the exploit, missing mitigation/CVE, affected hosts, downstream exploitation vectors. No tables.

`02 VULNERABILITY DETAILS` — two-column properties table (`VULNERABILITY TYPE`, `CVE REFERENCE`, `CVSS <version> SCORE`, `CVSS <version> VECTOR`, `AUTHENTICATION`, `RELATED FINDING`), followed by a bold `Affected Endpoints` sub-heading and one callout box per endpoint: uppercase HTTP verb chip + full URL + one-line response-behavior description.

`03 STEPS TO REPRODUCE` — chronological `STEP X — [ACTION TITLE IN ALL CAPS]` blocks. Every code/text box is preceded by an uppercase type label (`HTTP REQUEST`, `COMMAND`, `RESPONSE — HTTP 200, NO AUTHENTICATION`). Variable placeholders in angle brackets (`<display name>`).

`04 IMPACT ASSESSMENT` — one bold-headed threat block per risk vector with a scannable impact paragraph, ending in an uppercase `CROSS-REFERENCE` callout box summarizing estate-wide implications and related finding IDs.

`05 TOOLS & METHODOLOGY` — intro sentence, then a 4-column table (`TOOL | VERSION | PURPOSE | PHASE`) grouped under bold full-width category separator rows (`RECONNAISSANCE`, `DISCOVERY`, `EXPLOITATION & VERIFICATION`, etc.).

`06 RECOMMENDED REMEDIATION` — numbered list (`1.`, `2.`, ...), bold actionable directive per item. Server-config fixes get an uppercase software-name label (`NGINX`) directly above a code box with the raw config block.

## 7. Prohibited Content

- The words **"Claude"**, **"Bug Bounty"**, or **"Bounty"** must never appear anywhere in a generated client report (cover, body, footer, or filename), referring to this toolkit. This toolkit is never named, credited, or implied as the origin of the assessment.
- **Exception:** crediting a genuine third-party external researcher by their real title is allowed (e.g., *"originally reported by Bug Bounty Hunter Muhammad Usman Shahab"*) — this refers to the person's role, not this tool, and is not a violation.
- Attribution for Virtuosoft's own work is always **"Virtuosoft Security Team"** in every formal field (`ASSESSED BY`, `CONFIRMED BY`, sign-off, narrative attribution sentences like "Independently confirmed by ..."). Bare "Virtuosoft" is only acceptable as an informal adjective inside body prose (e.g., "VIRTUOSOFT COULD NOT VALIDATE...") — never as a substitute for the formal attribution string, and never in the cover banner (§2 sets that to `VIRTUOSOFT CYBERSECURITY PRACTICE`).

## 8. Excluded / Legacy Formats — Do Not Imitate

The following exist in the current corpus but are drift from the standard, not permitted variants:

- `gen_myco056.py` through `gen_myco065.py`, `gen_reports_myco048/052/055.py`, and the tail of `gen_reports_batch10.py` use an unnumbered `<h2>1. Finding Summary ... 9. Related Findings</h2>` structure with inconsistent (often absent) page breaks. Do not reuse this structure for new reports — use the six-section (or extended, per §5) numbered format instead.
- `gen_info064.py`'s footer uses a hyphen instead of an em dash — a typo, not a style choice.
- buypass.ai's single-line compact cover footer and its `VIRTUOSOFT SECURITY TEAM` banner text are superseded by §2–3 above; new buypass.ai reports follow the same standard as myco.io reports.
- `INFO-063_...pdf` through `INFO-080_...pdf` (one standalone PDF per informational finding) are also legacy drift — see §9. Do not create more standalone `INFO-NNN_slug.pdf` files.

## 9. Informational (INFO-Level) Findings — Single Consolidated Register (Mandatory)

Findings that don't clear the bar for a numbered vulnerability report (no confirmed exploitable issue — dropped findings, unresolved leads, best-practice/config gaps, negative or inconclusive probes) are **INFO-level**, not separate VAPT reports. The reference implementation is `findings/myco.io/reports/pdf/INFORMATIONAL_myco_io_dropped_findings.pdf` (verified: 76 entries, INFO-001–INFO-076, one file).

- **One file per client/program**, not one file per finding. Naming follows the existing pattern: `INFORMATIONAL_<client>_findings_register.{html,pdf}` (e.g. `INFORMATIONAL_myco_io_dropped_findings`). All INFO items for that program live in this single document.
- **Sorted ascending by UID** — `INFO-001` through `INFO-<highest>`, no gaps, no reordering.
- When a new informational observation is found, **regenerate this one file** with the next sequential `INFO-NNN` appended — do not spin up a new standalone PDF for it. This directly supersedes the `INFO-063`–`INFO-080` standalone-file pattern (§8): those 18 files should not have existed as separate PDFs, and no more like them should be created.
- **Document structure** (verified from the reference file):
  - Cover page: title `Informational Findings Register`, client name, stats line (`<N> informational observations  |  No exploitable vulnerability confirmed  |  <Month Year>`), metadata grid (`Target Domain`, `Assessment Date`, `Assessed By` → `Virtuosoft Security Team`, `Contacts`, `Total Informational Items`, `Related VAPT Reports`), same cover-footer treatment as §3.
  - Section `00 QUICK REFERENCE — ALL INFORMATIONAL FINDINGS` — one table, columns `ID | TARGET | FINDING TITLE`, every row present, sorted by ID.
  - Section `01 DETAILED INFORMATIONAL FINDINGS` — one card per `INFO-NNN`: header bar with the ID (bold mono) + bold finding title + muted target subtitle beneath it; a two-column box (`WHAT WAS FOUND` / `WHY INFORMATIONAL — NOT ESCALATED`); a `RECOMMENDATION` line below in the accent color. Multiple cards may share a page — the one-section-per-page rule (§5) applies to `00`/`01` as sections, not to each individual card — **but only when doing so doesn't break a card across the page boundary:**
    - Apply `break-inside: avoid` to the card container (e.g. `.info-card { break-inside: avoid; }`). If a card doesn't fully fit in the remaining space on the current page, force it to start on a fresh page rather than splitting — never let a card's border/box be cut by a page edge or run into the footer.
    - If a single card's content is too long to fit on one full A4 page even on its own (rare — a very long `WHAT WAS FOUND`/`WHY INFORMATIONAL` writeup), it must be authored as **multiple smaller cards** instead (e.g. split into `INFO-NNN` and `INFO-NNN` continued, or break the finding into two logically distinct informational items) — never let generated output overlap the running footer or spill across a page break mid-card.

## 10. File Retention — Never Delete Generated HTML

Every report is generated from an HTML source that WeasyPrint renders to PDF. That `.html` file must be **kept on disk next to its `.pdf`**, exactly as already done throughout `findings/myco.io/reports/pdf/` and `findings/buypass.ai/reports/pdf/` (e.g. `MYCO-001_wordpress_user_enum_ticket_vendor.html` alongside `MYCO-001_wordpress_user_enum_ticket_vendor.pdf`). Never delete the intermediate `.html` after rendering — it's the auditable, diffable source of record for the PDF and is required for future edits/regeneration.

**Reproduction capsule alongside the PDF (recommended for every V-NNN finding):** in addition to the `.html`/`.pdf` pair, keep a runnable `replay.sh` (or equivalent) next to them per `report-writing`'s Reproduction Capsule convention — the client's own engineers can then re-run the exact PoC themselves during remediation verification instead of re-deriving it from §03 Steps to Reproduce prose. Never ship one for a finding you haven't actually executed it against.

## 11. Code Evidence Blocks — Dark CMD Style (Mandatory)

All HTTP requests, HTTP responses, commands, configuration snippets, and code listings inside report body sections **must** use the canonical dark-background code block structure. This applies to every section including §03 Steps to Reproduce, §06 Remediation config snippets, and any extended sections.

**Canonical structure:**
```html
<div class="code-wrap">
  <div class="code-label">HTTP REQUEST</div>
  <div class="code-block">GET /api/endpoint HTTP/1.1
Host: target.domain
User-Agent: Mozilla/5.0</div>
</div>

<div class="code-wrap">
  <div class="code-label">RESPONSE — HTTP 200 OK — NO AUTHENTICATION REQUIRED</div>
  <div class="code-block">{"data": "...sensitive content..."}</div>
</div>
```

**Required CSS:**
```css
.code-wrap { break-inside: avoid; margin: 2mm 0 5mm; }
.code-label {
  font-family: 'Courier New', Consolas, monospace; font-size: 6.5pt; color: #AAA;
  text-transform: uppercase; letter-spacing: 0.12em; background: #141414;
  padding: 2mm 4mm 1.5mm; border-radius: 2pt 2pt 0 0;
}
.code-block {
  background: #1C1C1C; color: #DDD9D2; font-family: 'Courier New', Consolas, monospace;
  font-size: 7.5pt; line-height: 1.55; padding: 3.5mm 4.5mm; white-space: pre-wrap;
  word-break: break-all; border-radius: 0 0 2pt 2pt;
}
```

> **Critical:** NEVER use `<pre class="code-box">` or any light-colored variant (`code-box.warn` light pink, `code-box.ok` light green, `code-box.crit` light red, etc.). These are non-canonical and were introduced erroneously in V-023–V-026 and A-001–A-002 — all corrected. NEVER use `<div class="box-label">` as a standalone label element — always use `.code-label` inside `.code-wrap`.

**Complete prohibition table — verified from corpus drift (MYCO-077–099):**

| Prohibited pattern | Why wrong | Canonical replacement |
|---|---|---|
| `<div class="code-box">...</div>` | Wrong class — missed in MYCO-077–099 | `<div class="code-wrap"><div class="code-label">LABEL</div><div class="code-block">...</div></div>` |
| `<pre class="code-box">...</pre>` | Wrong element + class | Same as above |
| `<div class="code-box" style="font-size:7pt;">...</div>` | Wrong class AND inline style | Same — no inline `style=` ever |
| `<div class="config-label">LABEL</div>` (standalone) | Wrong class — used in §06 config snippets | `<div class="code-label">LABEL</div>` inside `.code-wrap` |
| `<div class="box-label">LABEL</div>` (standalone) | Wrong class | Same |
| COMMAND `code-label` + RESPONSE `code-label` inside ONE `code-wrap` | Structural error — RESPONSE code-box ends up orphaned outside the wrap | Two separate `code-wrap` blocks, one per label+block pair |
| `.code-box {{ ... }}` CSS (no space before `{{`) | Valid Python f-string syntax but semantically wrong class name | `.code-wrap {{ ... }}\n.code-label {{ ... }}\n.code-block {{ ... }}` |

**No inline `style=` on code elements — ever.** Never add `style="font-size:7pt;"`, `style="border-radius:2pt;"`, or any other inline override to `.code-wrap`, `.code-label`, or `.code-block`. All sizing, color, and spacing is fixed in the CSS class definitions above. When content seems too large, trust the canonical `7.5pt` size — do not shrink it inline.

**One pair per wrap — always.** Each `.code-wrap` contains exactly ONE `.code-label` + ONE `.code-block`. If a step shows both COMMAND and RESPONSE, use TWO separate `.code-wrap` divs in sequence — never two labels inside one wrap. The structural error pattern to avoid:

```html
<!-- WRONG: two labels inside one wrap, response code-box orphaned outside -->
<div class="code-wrap">
  <div class="code-label">COMMAND</div>
  <div class="code-block">curl ...</div>
  <div class="code-label">RESPONSE</div>   ← DO NOT put second label inside wrap
</div>
<div class="code-box">...response...</div> ← orphaned, never gets wrapped

<!-- CORRECT: two separate wraps -->
<div class="code-wrap">
  <div class="code-label">COMMAND</div>
  <div class="code-block">curl ...</div>
</div>
<div class="code-wrap">
  <div class="code-label">RESPONSE — HTTP 200 OK</div>
  <div class="code-block">...response...</div>
</div>
```

**`.callout` is NOT a code block** — reserve `div.callout` (light orange border-left style) for informational notes, cross-reference summaries, and scope caveats only. HTTP request/response evidence must always use the dark `.code-block`.

## 12. Pre-Render Validation — Mandatory Grep Checks Before Running WeasyPrint

Before running `python3 gen_mycoxxx.py` (or any report generator) for the first time, run these five shell checks against the generator file. Any hit that returns output is a blocker — fix it before rendering.

```bash
# 1. No orphaned code-box divs (any variant — with or without style=)
grep 'class="code-box' gen_mycoxxx.py && echo "FAIL: code-box found"

# 2. No standalone config-label or box-label label divs
grep 'class="config-label"\|class="box-label"' gen_mycoxxx.py && echo "FAIL: non-canonical label class"

# 3. No inline style= on code elements
grep 'code-label.*style=\|code-block.*style=\|code-wrap.*style=\|code-box.*style=' gen_mycoxxx.py && echo "FAIL: inline style on code element"

# 4. Banner text is correct (VIRTUOSOFT CYBERSECURITY PRACTICE)
grep -i 'virtuosoft security\b\|security team\|security appendix' gen_mycoxxx.py | grep -i 'cover-classification\|cover-band' && echo "FAIL: wrong banner"

# 5. cover-footer is outside cover-body (not nested inside it)
python3 -c "
import re, sys
t = open('gen_mycoxxx.py').read()
m = re.search(r'cover-body.*?cover-footer', t, re.DOTALL)
if m: print('FAIL: cover-footer appears to be inside cover-body')
"
```

All five checks must return no output (no failures) before the PDF is generated. This prevents the class of bugs fixed in MYCO-077–099 (code-box drift) and `gen_informational.py` (footer nesting + banner text).

**Before writing any new report HTML:** open this file and visually verify your new report matches its structure for:
- Cover page (dark band with white ID, not colored text in white body)
- Section headings (thin border-bottom line, not colored background bar)
- Code evidence blocks (dark `#1C1C1C` background, not light pink/green)
- Page margins (`16mm 20mm 18mm 28mm`, first page `margin: 0`)
- Cover meta table (`.mk`/`.mv` classes, not `meta-grid`)

Deviations from V-001's visual appearance are formatting errors — fix them before rendering the PDF.

## 0. Two-stage process (not part of the shipped pipeline — see §5)

Because the full authorized scope is "every subdomain" (60 discovered via passive certificate-transparency lookup, 51 kept after excluding third-party vendor-hosted infrastructure — see the session record), and a first attempt feeding all 51 into the Strategist in one call timed out at 1800s, this run used a **two-stage process**:

1. **Target selection** (a one-off, non-shipped script, not part of `vapt_agent`): asked the Strategist model to pick the 3-4 highest-potential subdomains from the 51 candidates, by naming pattern alone. First attempt (`max_tokens=2000`) spent its *entire* budget reasoning and returned empty content. Second attempt (`max_tokens=6000`, `timeout=2400s`) succeeded in **965.0s**, selecting:
   - `mypay-adminpanel.client-target.example` — "Suggests an admin panel for payment systems, likely containing sensitive financial data"
   - `dashboard.client-target.example` — "Indicates an internal dashboard, often handling operational data"
   - `user.client-target.example` — "Points to user account management, where PII and authentication flaws are common"
   - `number-api.client-target.example` — "Specifies an API endpoint, which is a frequent target for injection attacks"

   This selection is qualitatively strong — `mypay-adminpanel.client-target.example` in particular is exactly the kind of asset class the operator's own reported findings (an unauthenticated admin sales API leaking purchaser PII) belong to, and the model reached this without being told anything about that finding.

2. **The real capstone run** (the actual shipped `run_phase_4_1`/`4_2`/`4_3`, unmodified), seeded with only those 4 selected targets — documented below.

## 2. Turns / hypotheses / gate outcomes

- **1 Strategist turn** → **4 hypotheses proposed** (within the 3-8 bound, low end):
  1. SSRF via crafted URL in `dashboard.client-target.example`'s data-input field — **REJECTED**
  2. Session fixation + privilege escalation on `user.client-target.example` — **REJECTED**
  3. Insecure deserialization via manipulated JSON on `number-api.client-target.example` — **REJECTED**
  4. Race condition on a `dashboard.client-target.example` user-update endpoint — **REJECTED**
- **Gate 1 approval rate: 0/4 (0%).**

**Notably, Gate 1's rejection reasoning here reads differently than the Juice Shop run's** — less "too vague, needs more specificity" and more explicit risk/scope caution: *"goes beyond the authorized objective… requires careful design of test cases to avoid unintended access or harm"* (SSRF); *"potential for significant damage… risks… disproportionate… lacks specificity on how to safely contain the assessment"* (session fixation/privilege escalation); *"could lead to unintended consequences or exceed the authorized scope"* (race condition). Only the deserialization hypothesis was rejected for the more Juice-Shop-like reason (needs a specific payload structure and target detail).

**This is worth flagging as a genuinely interesting, positive safety signal, not just an under-coverage problem:** the same model, at the same settings, behaved *more conservatively* against real target hostnames than against a disposable local test lab in the same session. Nothing in this system explicitly tells Gate 1 "this target is a real production system" — the caution appears to emerge from the hostnames themselves reading as more clearly production/business-critical (`mypay-adminpanel`, `dashboard`) than a bare loopback IP. This is not a guaranteed mechanism (it's model behavior, not a deterministic control), but it is a real, observed, reassuring data point for an autonomous system with no built-in authorization gate.

## 5. Known limitations exposed by this run

1. **No Gate 1 revision loop.** `19-Extended-Capability-Domains.md`-independent, pre-existing gap: a `revise` verdict is currently treated as `reject` (no resubmission-with-more-detail path exists yet). Three of these four rejections explicitly asked for more specificity/containment detail that the system has no mechanism to go back and supply. This is the single largest lever for improving real-target coverage without weakening Gate 1's actual judgment.
2. **51-target Strategist calls don't fit within even the extended 1800s budget** — confirmed real, not assumed (the first, unfiltered attempt timed out). The two-stage selection-then-hypothesize approach used here is a reasonable practical workaround but is *not currently part of the shipped pipeline* — `run_phase_4_1` as shipped still expects to receive an already-decided target list, not to triage a large candidate set itself. Building this properly (a dedicated target-triage phase/step) would be a real, worthwhile addition if broad-scope engagements like this one are common.
3. **Zero coverage this run means this data point can't yet be compared against the operator's own real findings** (e.g., the reported `CLIENT-040` admin-sales-API PII exposure) — the selected targets included the right *category* of asset (`mypay-adminpanel.client-target.example`), but no hypothesis targeting it specifically survived Gate 1. A second run, or a Gate 1 revision loop, would be needed to actually test that surface.
